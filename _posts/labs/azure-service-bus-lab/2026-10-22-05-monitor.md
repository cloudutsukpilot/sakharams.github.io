A message broker is easy to use and hard to see into: the interesting state (how many messages wait,
how often one was retried, which subscription is falling behind) lives in Azure, not in your app.
This part tours the lab's dashboard panel by panel, shows the query behind each one, and says how
long each signal takes to show up. By the end you'll know where to look for each experiment.

## Open the Dashboard
{: #open-the-dashboard }

https://grafana.mon.home.cloudutsuk.com → Dashboards → Labs → **Azure Service Bus Queues and Topics**
(uid `azure-service-bus-lab`). It refreshes every 10 s and shows the last 15 minutes. The **Order**
box at the top filters the log panel: paste an order id (`ord-xxxxxx`) from the Shop page to see only
that order's lines.

The Shop and Playground pages show the same entity counts as the top row, from the same source, every
3 s. Use the pages while you act and the dashboard to see what happened over time.

{: #panel-by-panel }

Every query filters on `cluster="lab-servicebus"` (metrics), `k8s_cluster_name="lab-servicebus"`
(logs) or `resource.k8s.cluster.name = "lab-servicebus"` (traces), because mon holds every cluster's
data. They're shortened below.

|---|---|---|---|

A few things are worth knowing when you read them:

- **Two kinds of numbers.** Panels 1–3, 5 and 11 come from Azure (the management API's counts); they
  tell you the state of an entity no matter who touched it, the Playground and `az` included. Panels 4
  and 6–10 come from the app's own counters; they tell you what *this* code did. When the two disagree,
  something outside the app acted on the entity.
- **Active includes locked.** A message being processed is still active until it's completed. With
  one worker and a backlog, panel 1 never drops below the number of locked messages.
- **`increase()` over a short range estimates.** Prometheus extrapolates, so panel 4 can read 1.9 for
  two sends. Compare shapes and orders of magnitude, not decimals.
- **analytics never shows in panel 9.** Nothing settles its messages. Look for it in panel 5 instead,
  where it climbs and stays.

## Explore Queries
{: #explore-queries }

For anything the panels don't show, use Explore with the same data sources (`mimir`, `loki`, `tempo`).

Every delivery of one order, with its delivery count:

```logql
{k8s_cluster_name="lab-servicebus", service_name="sblab-fulfillment"} |= "ord-29fbf1" | logfmt
```

Abandons per pod in the last 10 minutes:

```promql
sum by (worker) (increase(sblab_messages_settled_total{cluster="lab-servicebus", entity="orders", outcome="abandoned"}[10m]))
```

Orders whose processing failed, as traces:

```traceql
{ resource.k8s.cluster.name = "lab-servicebus" && name = "orders process" && status = error }
```

Traces that reached fraud-review:

```traceql
{ resource.k8s.cluster.name = "lab-servicebus" && name = "fraud-review process" }
```

And Azure's own view, without Grafana:

```bash
make azure-status
az servicebus topic subscription rule list -g rg-sb-lab --namespace-name "$(cat .state/namespace)" \
  --topic-name order-events --subscription-name fraud-review -o table
```

## Signal Timing
{: #signal-timing }

| Signal | Path | Delay before you can see it |
|---|---|---|
| Shop page live feed | worker → `POST /internal/activity` → server-sent events | under a second |
| Entity counts on the pages | management API, polled by the page every 3 s (the server refreshes every 5 s) | up to about 8 s |
| `sblab_entity_messages` in Grafana | the 5-second poll, exported every 10 s, then the collectors | 10–30 s |
| Counters and histograms | exported every 10 s | 10–30 s |
| Logs | OTLP, batched | a few seconds |
| Traces | OTLP, batched; Tempo's search index lags | up to about a minute before a trace is searchable |

That's why each experiment's `wait` is 30 to 60 seconds, and why the trace experiments keep a
`verify` step: `scripts/signal.sh` retries a missed search six times, ten seconds apart.

## Check Your Understanding
{: #check-your-understanding }

<details markdown="1">
<summary>Panel 1 says 5 orders are waiting, but no worker has logged a receive for a minute. Where would you look?</summary>

At the fulfillment pods: are any running (`kubectl -n shop get pods`), and is their log showing
connection errors? Panel 1 counts what Azure holds; if nothing receives, active stays up. Panel 7
staying flat for `orders` confirms nobody is settling.

</details>

<details markdown="1">
<summary>Why does the app poll the management API instead of counting sends minus completes?</summary>

Because its own counters miss everything outside the app: messages sent from the Playground with
another key, from `az` or another service, messages that expired or were dead-lettered by the broker,
scheduled messages that haven't appeared yet. Only Service Bus knows the real count.

</details>

<details markdown="1">
<summary>A trace exists in Tempo but `make verify-one-order` failed once. Why might that be fine?</summary>

Tempo's search index lags ingestion by up to about a minute. The trace can be stored but not yet
searchable; `signal.sh` retries for that reason, and a later attempt finds it.

</details>
