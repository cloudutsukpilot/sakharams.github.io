## Bring It Up
{: #bring-it-up }

Sign in to Azure on the DGX and pick the subscription the lab should bill:

```bash
az login
az account set --subscription "<name or id>"
```

Then, from `azure-labs/service-bus`:

```bash
make up
```

`up` runs, in order:

| Target | What it does |
|---|---|
| `azure-up` | Checks `az account show`, then `infra/up.sh`: resource group, Standard namespace, queues, topic, subscriptions, rules, the three access policies, then `.state/lab.env` and `.state/connections.env` |
| `cluster` | `k3d cluster create --config k3d/cluster.yaml` (skipped if `lab-servicebus` exists) |
| `dns` | CoreDNS upstreams for pods on the homelab network |
| `secret` | `.state/connections.env` → Secret `shop/servicebus` |
| `build` | `docker build -t sblab:dev app`, `k3d image import` |
| `deploy` | `kubectl apply -k k8s`, then waits for `shop-web`, `fulfillment` and `subscribers` |
| `monitoring` | `lab.sh register lab-servicebus dashboards`: Argo CD, the monitoring pack, the dashboard |

Creating the namespace is the slow Azure step (it is provisioned, then each entity is a quick
management call); the monitoring pack is the slow cluster step. `up.sh` is safe to re-run: `create`
on an existing entity updates it to the script's settings.

From the portal's **Labs** page, **Deploy** runs the same `make up` through the lab runner, after
asking you to confirm the cost, and **Destroy** runs `make down`. The runner destroys the lab by
itself after 4 hours unless you extend it.

## Verify the Rollout
{: #verify-the-rollout }

```bash
make status
```

`status` is the lab's preflight, and it fails unless all three hold:

1. `kubectl get pods -n shop` lists `shop-web`, `fulfillment` and `subscribers` Running and Ready.
2. infra-local's `lab.sh status` shows `monitoring-pack-lab-servicebus` as `Synced/Healthy`.
3. `GET /api/entities` answers with the namespace's entities and no error, which proves the app's
   Manage key works and the pod reaches Azure: `servicebus: ok, 9 entities` (three queues, the topic
   and its five subscriptions).

And from Azure's side:

```bash
make azure-status
```

prints the namespace's SKU and status, then every queue and subscription with its active, dead-letter
and scheduled counts, as Azure reports them. Compare it with the Shop page's table at any point in the
lab: the two should agree to within the page's 3-second refresh.

## Smoke Test
{: #smoke-test }

Open http://127.0.0.1:8095/ (or https://servicebus.labs.home.cloudutsuk.com/ from the tailnet). The
right-hand table lists `orders`, `playground`, `playground-sessions` and the five `order-events/…`
subscriptions with their rules, all at zero.

Place one order with the defaults (ana, EU, 120 USD). Within a few seconds its card in the middle
column fills in, in this order (the steps and text from the emulator run, without the times):

```text
sent        to orders checkout
locked      from orders, attempt 1 (delivery count 0) fulfillment-a
completed   removed from orders fulfillment-a
published   OrderConfirmed to order-events fulfillment-a
delivered   billing got OrderConfirmed: invoice INV-ef8bab for 120.0
delivered   email got OrderConfirmed: confirmation email to ana
published   OrderShipped to order-events subscribers-a
delivered   shipping got OrderConfirmed: packed and shipped; published OrderShipped
delivered   email got OrderShipped: shipping notice email to ana
```

The chips under it light `billing`, `shipping` and `email`. `fraud-review` stays dark (the order is
under 500 USD), and so does `analytics`, whose count in the right-hand table goes up by two instead:
nobody reads it.

From the command line:

```bash
make traffic      # ten random orders
make logs         # follow the three workloads
```

Then open the Playground, send a message to `playground` and **Peek** it. If you can send, peek,
receive and complete there, every part of the lab works.

## Common Failures
{: #common-failures }

| Symptom | Cause | Fix |
|---|---|---|
| `not signed in to Azure: az login` from `make up` | No az session on the DGX (or the lab runner's user) | `az login`, `az account set` |
| `The namespace name is not available` or a `Conflict` from `up.sh` | Someone else holds `sblab-<suffix>` (very unlikely), or one was just deleted | `rm .state/namespace` and re-run; a new suffix is generated |
| Pods `CreateContainerConfigError` | The Secret `shop/servicebus` is missing | `make secret` (needs `.state/connections.env` from `make azure-up`) |
| The Shop table shows an error with `ServiceBusConnectionError` or a timeout, `make status` fails on `servicebus:` | Outbound TCP 5671 blocked between the DGX and Azure | Set `SB_TRANSPORT=websocket` on the three Deployments (AMQP over WebSockets on 443) and `make deploy` |
| 401 `ServiceBusAuthorizationError` in normal shop use | A Deployment got the wrong key (edited `app.yaml`) | Check the `secretKeyRef`s against the comment at the top of `app.yaml` |
| A message to `playground-sessions` is refused: "The SessionId was not set on a message" | It's a session queue: every message needs a SessionId | Fill **SessionId** in the Playground |
| Counts in the table stay at `?` | You're on the emulator dev loop, not Azure: its counts don't parse in the Python SDK | Expected there; on Azure they're numbers |
| `make up` refused by the portal: ports in use | Something already listens on 8095 or 6452 (often the lab started with `make up` outside the portal) | `make down`, or stop what holds the port |
| Grafana shows the dashboard but no data | Time picker, or the monitoring pack isn't Healthy yet | Last 15 minutes; `make status`; `make monitoring` again |

## Check Your Understanding
{: #check-your-understanding }

<details markdown="1">
<summary>Why does `make up` create the Azure side before the cluster?</summary>

The pods read their connection strings from the Secret `shop/servicebus`, which `make secret` builds
from `.state/connections.env`, which `infra/outputs.sh` writes after the namespace and its policies
exist. Without the keys the Deployments can't start.

</details>

<details markdown="1">
<summary>`make status` calls /api/entities. What does a success there prove that "pods Running" doesn't?</summary>

That shop-web can resolve and reach the namespace, that its Manage key is valid, and that the entities
`up.sh` created are there. A pod can be Running with a wrong key or no route to Azure.

</details>

<details markdown="1">
<summary>analytics' count went up by two for one order. Why two?</summary>

Two events about the order reached the topic: OrderConfirmed from fulfillment and OrderShipped from
shipping. analytics' `$Default` rule matches both, and nobody receives from it.

</details>
