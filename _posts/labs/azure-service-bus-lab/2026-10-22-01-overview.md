In this lab you run a small online shop on a real Azure Service Bus namespace. Checkout drops each
order on a queue, fulfillment workers take them off one at a time, and a topic tells billing,
shipping, fraud review and email about every confirmed order. A Playground page next to the shop lets
you make every Service Bus call by hand. By the end of this part you'll know what each piece does and
how one order travels through all of them.

## What You Will Build
{: #what-you-will-build }

Most explanations of Service Bus stop at "a producer sends, a consumer receives". The interesting
part is what happens *around* that: a worker that crashes halfway, a customer who double-clicks
**Place order**, a sale that sends sixty orders in a second, a card that is always declined, a
service that's been switched off for an hour. This lab gives each of those a button, and shows you
what Service Bus does about it.

The shop has three parts, all small Python services on a k3d cluster on the DGX Spark:

- **Checkout** (`shop-web`) only *sends*. It puts the order on the `orders` queue and answers the
  browser straight away. It never waits for payment.
- **Fulfillment** takes one order at a time from the queue, charges the card (simulated), publishes an
  `OrderConfirmed` event to the `order-events` topic, and only then marks the order done. Scale it to
  three pods and they share the queue.
- **Subscribers** hold one receiver per topic subscription: billing writes an invoice, shipping packs
  the order and publishes `OrderShipped`, fraud review looks at expensive orders, email sends a
  message per event.

The Service Bus side, a Standard namespace with two queues, a session queue, a topic and five
subscriptions, is created with the az CLI and deleted when you're done. Everything the services do
ends up as traces, metrics and logs in the homelab's Grafana, so you can see a message wait, get
locked, fail, retry and land in the dead-letter queue.

Two pages make it hands-on:

| Page | What you do there |
|---|---|
| **Shop** (`/`) | Place orders (normal, over 500 USD, sent twice, scheduled, with a declined card, or 30 at once), watch each order's journey live, and resubmit dead-lettered orders |
| **Playground** (`/playground`) | Send to any queue or the topic with your own properties, peek, receive in peek-lock or receive-and-delete mode, then complete, abandon, dead-letter, defer or renew each message; read the dead-letter sub-queue and sessions; switch between a send-only, listen-only and manage key |

The code is in `labs-azure/service-bus` (private for now), and one command brings it all up:

```bash
make up    # Azure namespace and entities, k3d cluster, Secret, image, app, join the platform
```

## Architecture
{: #architecture }

Step through one order. The checkbox switches it to an 800 USD order, which a fifth subscription
also wants.

{% include flow-anim.html id="labs/azure-service-bus-lab/architecture" %}

No service in this picture calls another. Checkout doesn't know fulfillment exists, fulfillment
doesn't know who listens to `order-events`, and adding a sixth subscriber changes no code anywhere
else. That is what the broker in the middle buys you, and every experiment in this lab pokes at one
consequence of it.

| Component | Role | Runs |
|---|---|---|
| `shop-web` | Shop and Playground pages, checkout, entity counts, live feed | k3d, 1 pod |
| `fulfillment` | Receives from `orders`, publishes `OrderConfirmed` | k3d, 1 to 3 pods |
| `subscribers` | One receiver each for billing, shipping, fraud-review, email | k3d, 1 pod |
| queue `orders` | Holds orders until a worker completes them; 3 deliveries max, then dead-letter; duplicate detection | Azure |
| topic `order-events` | Copies each event into every subscription whose rule matches | Azure |
| 5 subscriptions | `billing`, `shipping`, `fraud-review`, `email`, `analytics` (nobody reads it) | Azure |
| queues `playground`, `playground-sessions` | Free play from the Playground page | Azure |
| monitoring pack and `mon` | Collect and store the lab's traces, metrics and logs | homelab |

## Building Blocks
{: #building-blocks }

### Azure Service Bus

A managed message broker. You create a **namespace** (`<name>.servicebus.windows.net`) and inside it
**queues** (one sender, one of many receivers gets each message) and **topics** (each message is
copied into every matching **subscription**, and each subscription is then read like a queue). It
keeps messages until a receiver settles them, retries them, and parks the ones that keep failing in a
**dead-letter queue**. The lab's entities are all in
[infra/up.sh](/posts/labs/azure-service-bus-lab/03-set-up-infrastructure/#the-cluster).

### The azure-servicebus Python SDK

Microsoft's client library (7.14.3 here). It speaks AMQP 1.0 to the namespace on port 5671, and has a
separate management client that talks HTTPS to read entity counts. Every call the Playground makes is
one or two lines of it; [Part 2](/posts/labs/azure-service-bus-lab/02-write-the-code/#the-application)
walks through them.

### FastAPI and plain JavaScript

`shop-web` is a FastAPI app (0.115) that serves two static pages and a JSON API. The pages are plain
HTML and JavaScript with no build step, so what you read in the repo is what runs in the browser.

### k3d on the homelab platform

The three services run on `lab-servicebus`, a one-node k3d cluster that joins the homelab's `homelab`
Docker network (lab contract v2). Argo CD installs the monitoring pack into it, and the lab keeps no
Grafana of its own.

### OpenTelemetry

Each process runs under `opentelemetry-instrument`, which exports traces, metrics and logs over
OTLP. Service Bus doesn't pass trace context by itself, so every producer writes a W3C `traceparent`
into the message's application properties and every consumer continues from it. That is how one trace
can cross three services that never talk to each other.

## Check Your Understanding
{: #check-your-understanding }

<details markdown="1">
<summary>Checkout answers the browser before the card is charged. What happens to the order if every fulfillment pod is down for ten minutes?</summary>

Nothing bad. It waits in the `orders` queue, counted as active, until a worker receives it. The
queue's default time to live is one day, so the order is still there when fulfillment comes back, and
the customer's checkout never noticed.

</details>

<details markdown="1">
<summary>Why does billing get a copy of every confirmed order, but fraud-review only some?</summary>

Each subscription has its own rule. billing's correlation filter matches every message whose subject is
`OrderConfirmed`; fraud-review's SQL filter also wants `total > 500`. The topic evaluates each rule
against the message's properties and copies the message only into the subscriptions that match.

</details>

<details markdown="1">
<summary>Nobody reads the analytics subscription. Does that slow down billing?</summary>

No. Each subscription is an independent queue with its own messages, receivers and counts. analytics
just fills up (until its messages' time to live), and billing never sees it.

</details>

<details markdown="1">
<summary>Why would you pick a topic over sending the same order to four queues?</summary>

With four queues the sender has to know every consumer and send four times, and adding a fifth means
changing the sender. With a topic it sends once, and a new consumer is a new subscription with a rule:
nothing on the sending side changes.

</details>
