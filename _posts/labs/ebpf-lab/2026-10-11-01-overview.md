This lab swaps a k3d cluster's networking for Cilium, gets request metrics and traces out of a Go service
that has no telemetry code, and catches (then kills) a download attempt inside a container. All of it is
done with eBPF. By the end of this part you'll know what the lab builds, what your machine needs, and
which program sees which part of a request.

## What You Will Build
{: #what-you-will-build }

A two-node k3d cluster, `lab-ebpf`, running a deliberately plain app:

- **web**: nginx serving one page, proxying `/api/` to the API.
- **api**: a Go HTTP service with two replicas, one per node. It counts visits in Redis. There's no
  OpenTelemetry, no metrics library and no logging middleware in it, on purpose.
- **redis**: one Redis with append-only persistence, on a PersistentVolumeClaim bound to a static local
  PersistentVolume. The counter survives deleting the whole cluster.

Around the app, four eBPF tools watch from the kernel:

| Tool | What it does here |
|---|---|
| **Cilium** | The cluster's only network layer. It replaces flannel, kube-proxy and k3s's network policy controller. Hubble shows every flow it forwards or drops |
| **OpenTelemetry eBPF Instrumentation (OBI)** | Reads the app's HTTP and Redis traffic and turns it into request-rate, error and duration metrics and trace spans |
| **Tetragon** | Records process executions in the app's pods and enforces a policy in the kernel: it kills any process that tries to start `wget`, `curl` or `nc` |
| **Falco** | Matches syscalls against rules and raises alerts, such as a shell started in a demo pod |

The lab bundles no Grafana, Prometheus, Loki or Tempo. It's a lab on the Cloudutsuk homelab platform
([lab contract v2](/posts/projects/cloudutsuk-platform/11-infrastructure-and-environments/#lab-contract-v2)):
`make up` registers the cluster with the platform, Argo CD installs the monitoring pack into it, and every
metric, log and trace lands in the shared `mon` cluster under `cluster="lab-ebpf"`. The lab's own
dashboard is in `mon`'s Grafana, folder **Labs**.

The repo is `~/gitrepos/observability/ebpf-lab`. From there, one command brings it all up:

```sh
make up
```

> eBPF programs run in the host's kernel, not in the node containers. On a shared host, Tetragon and Falco

## Architecture
{: #architecture }

Step through one visit, then follow each tool's signal to where you'll read it:

{% include flow-anim.html id="labs/ebpf-lab/architecture" %}

| Component | Role | Runs where |
|---|---|---|
| `web` (nginx 1.29) | Serves the page, proxies `/api/` | Deployment, 1 replica, NodePort 30091 (host 8091) |
| `api` (Go) | `/api/visits`, `/api/items`, `/healthz` | Deployment, 2 replicas spread over both nodes |
| `redis` (7.4.2) | The visit counter, append-only file on a PVC | Deployment, 1 replica, on the server node (where its PV is) |
| Cilium 1.20.2 + Hubble | CNI, kube-proxy replacement, network policy, flow visibility | DaemonSet `cilium` per node, Hubble Relay and UI (NodePort 30092) |
| OBI 0.13.0 | HTTP and Redis RED metrics and spans from eBPF | DaemonSet `obi` on the host network, namespace `obi` |
| Tetragon 1.7.1 | Process events and in-kernel enforcement | DaemonSet `tetragon`, events on its `export-stdout` sidecar |
| Falco 0.45 + Falcosidekick | Syscall rules, alerts and an event UI | DaemonSet `falco` (modern eBPF probe), UI on NodePort 30093 |
| Monitoring pack | Agent and cluster collectors, kube-state-metrics | Namespace `monitoring`, installed by Argo CD from the platform |
| `mon` | Gateway, Mimir, Loki, Tempo, Grafana | The homelab's monitoring cluster, shared by every cluster |

The two node containers share the host's kernel, so "per node" for an eBPF tool means "per k3d node
container": each DaemonSet pod loads its programs into the same kernel, and filters by the processes and
interfaces of its own node.

## Building Blocks
{: #building-blocks }

### eBPF

eBPF lets you load small, verified programs into the Linux kernel and attach them to events: a packet
arriving on an interface, a function being called, a syscall being made. The programs keep state in maps
that user-space agents read. Every tool in this lab is such an agent. None of them needs a change to the
app or a sidecar in its pods.

### Cilium and Hubble

[Cilium](https://cilium.io) is a Kubernetes network layer built on eBPF. Here it does three jobs that k3s
would otherwise do with flannel, kube-proxy and iptables: pod networking (VXLAN between the two nodes),
Service load balancing, and network policy, enforced by security identity rather than IP address. Hubble
is its observability layer. Part 3 walks through [its settings](/posts/labs/ebpf-lab/03-set-up-infrastructure/#the-cluster).
The blog's [Network Policies](/posts/devops/orchestration/kubernetes/kubernetes-network-policies/)
post covers the Kubernetes side of policy.

### OpenTelemetry eBPF Instrumentation (OBI)

OBI is the OpenTelemetry project that Grafana Beyla was donated to. It attaches eBPF probes to processes
it's told to watch, decodes protocols such as HTTP and Redis on their sockets, and exports
OpenTelemetry metrics and spans. Part 2 explains what that means for an app that has no telemetry code.

### Tetragon

[Tetragon](https://tetragon.io), from the Cilium project, traces process execution and arbitrary kernel
functions, adds Kubernetes metadata, and can act inside the kernel: send a signal, override a return value.
The lab uses it to kill network tools before they start.

### Falco

[Falco](https://falco.org), a CNCF project, watches syscalls with its modern eBPF probe and evaluates
rules against them. It detects and reports; it doesn't block. Falcosidekick forwards its alerts and runs a
small web UI.

### k3d, Redis and the platform

k3d runs k3s nodes as Docker containers. Redis keeps the counter. The platform pieces (Argo CD, the
monitoring pack, `mon`) are the same ones every homelab cluster uses; the
[OpenTelemetry lab](/tags/opentelemetry-lab/) is the other lab built on them.

## Check Your Understanding
{: #check-your-understanding }

<details markdown="1">
<summary>The API has no OpenTelemetry SDK. Where can request metrics for it come from?</summary>

From outside the process. OBI's eBPF probes see the API's HTTP requests and responses and its Redis
commands at the kernel and runtime level, time them, and export the result as OpenTelemetry metrics and
spans. The API's code never knows.

</details>

<details markdown="1">
<summary>Why do Tetragon and Falco need filters for namespace <code>demo</code> on this machine?</summary>

Because their programs run in the one kernel every container on the host shares. Without a filter they
would report processes from the other homelab clusters, Docker and the desktop too. Their Kubernetes
metadata only covers pods of `lab-ebpf`, so the lab keeps events whose namespace is `demo`.

</details>

<details markdown="1">
<summary>The lab has no Grafana of its own. How does a metric from OBI reach a dashboard?</summary>

OBI exports OTLP to the homelab's gateway on `mon`, with the shared labs token and
`k8s.cluster.name=lab-ebpf`. The gateway turns that into the label `cluster="lab-ebpf"` and writes the
metric to Mimir. The lab's dashboard in `mon`'s Grafana filters every query on that label.

</details>

<details markdown="1">
<summary>What would you need to change to run a second copy of this lab next to the first, besides the cluster name?</summary>

All four host ports, 6450 (API), 8091, 8092 and 8093, and the pod and Service ranges. k3d fixes port mappings
when it creates the cluster, and two clusters on the `homelab` network can't share a range.

</details>
