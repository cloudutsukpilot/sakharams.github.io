Your Foundry account has public network access switched off, and your DGX Spark sits on a home
network. This lab connects the two for about $14 a month, without a VPN Gateway. By the end of this
part you'll know what gets built, what it costs, and which way a DNS query and a request travel
before an SDK call from the DGX gets a `200`.

## What You Will Build
{: #what-you-will-build }

A call from the DGX to a private endpoint needs two things, and missing either one gets you the same
`403 Public access is disabled`:

1. **A network path into the VNet.** A WireGuard tunnel from the DGX to a small Linux VM in the VNet.
   The VM forwards the traffic and NATs it to the private endpoint.
2. **A private DNS answer on the DGX.** The account's public name is a CNAME into a `privatelink.*`
   zone. Only resolvers inside a VNet linked to that zone get the private IP. The DGX sends just the
   three Azure AI domains through the tunnel to dnsmasq on the VM (split DNS). Everything else keeps
   using your home router.

The lab builds a complete, disposable copy of that setup in its own resource group: a VNet, a Foundry
(`AIServices`) account with public access disabled, its private endpoint and DNS zones, and the
WireGuard VM. Everything is created with the `az` CLI. On the DGX it adds one WireGuard interface,
`wg0`, and three `resolvectl` routing domains.

So you can see each step take effect, a small probe on the DGX calls the account's three names every
10 seconds. It reports the DNS answer, the path (private or public) and the HTTP status to a local
Grafana as metrics, logs and traces. You make one change at a time and watch the dashboard react.

```sh
cd private-connectivity-labs/azure-private-endpoint
make azure-up     # about 10 minutes: everything on the Azure side
make probe-up     # local Grafana on http://localhost:3012 and the probe
```

### Why not a VPN Gateway?

I priced the managed options before choosing a VM:

| Option | Per month | Notes |
|---|---|---|
| **WireGuard VM** (this lab) | **about $12 to $14** | You patch one small VM |
| Same VM, deallocated when idle | about $6 | IP and disk only; the tunnel comes back on its own ([Experiment 6](/posts/labs/azure-private-endpoint-lab/06-experiments/#exp-vm-start)) |
| Tailscale subnet router on the same VM | same as the VM | No inbound port, but the VM still needs outbound internet (a public IP or a NAT Gateway) |
| VPN Gateway `VpnGw1AZ`, point-to-site | about $157 ($0.21/h + IP) | Fully managed, and you still have to solve DNS |
| VPN Gateway `Basic` | about $26 | Needs a Basic public IP, a SKU Azure has retired; a dead end for new builds |
| DNS Private Resolver (inbound endpoint) | $180 | The managed replacement for the lab's free dnsmasq |
| `/etc/hosts` entries on the DGX | $0 | Works until the endpoint is recreated and its IPs change |

For one machine at home, a VM is about a tenth of the price of the gateway, and the DNS part is free.

## Building Blocks
{: #building-blocks }

### Private endpoint and Private DNS

A private endpoint is a NIC in your VNet that leads to one Azure resource. Turning off public access
on the resource means only traffic arriving through such an endpoint is let in. The catch is the
name: clients still call `<account>.openai.azure.com`, and something has to resolve that name to the
endpoint's IP. Azure does it with a CNAME to `<account>.privatelink.openai.azure.com` plus a private
DNS zone of that name, linked to the VNet. Background:
[Azure - Private Endpoints](/posts/cloud/azure/networking/private-endpoints/).

### Microsoft Foundry account (`AIServices`)

The account behind Foundry projects and Azure OpenAI deployments. One account answers on three
public names (`cognitiveservices.azure.com`, `openai.azure.com`, `services.ai.azure.com`), and each
has its own `privatelink` zone. The lab creates one with public access disabled and calls
`GET /openai/models` on it, which needs no model deployment and costs no tokens.

### WireGuard

A VPN built into the Linux kernel: one UDP port, a key pair per peer, and a list of `AllowedIPs` that
decides both what is routed into the tunnel and what is accepted out of it. There's no handshake
daemon and no certificates. Here it's a split tunnel: only the VNet goes through it. Background on
the managed alternative: [Azure - Virtual Network Gateway](/posts/cloud/azure/networking/azuure-virtual-network-gateway/).

### dnsmasq

A small DNS forwarder. On the VM it listens on the tunnel address only and forwards every query to
Azure DNS. It does the same job as a DNS Private Resolver inbound endpoint, for free.

### systemd-resolved split DNS

Ubuntu's resolver keeps DNS settings per network link. A domain prefixed with `~` is a *routing
domain*: queries for names under it go to that link's DNS server and nowhere else. That is how the
DGX sends three domains to Azure and everything else to the router.

### Azure VNet

The private network the endpoint lives in: `10.60.0.0/16` with `snet-pe` for the endpoint and a
`/28` `snet-vpn` for the VM. Background: [Azure - Virtual Networks](/posts/cloud/azure/networking/azure-virtual-networks/).

### OpenTelemetry and Grafana LGTM

The probe uses the OpenTelemetry Python SDK to push metrics, logs and traces over OTLP to
`grafana/otel-lgtm`, a single container with Grafana, Prometheus, Loki and Tempo. It's only there so
you can see each change. The connectivity works without it.

## Check Your Understanding
{: #check-your-understanding }

<details markdown="1">
<summary>The DGX can reach 10.60.1.5 over the tunnel. Why does an SDK call still fail?</summary>

The SDK connects to whatever the name resolves to. Until the DGX asks a resolver that sees the
linked private zone, `<account>.openai.azure.com` resolves to the public IP, the call goes over the
internet, and the account's firewall rejects it with `403`. Routing and DNS are two separate halves.

</details>

<details markdown="1">
<summary>Why can't the DGX use 168.63.129.16 directly through the tunnel?</summary>

`168.63.129.16` is a virtual IP that answers only for traffic coming from an Azure VM's own NIC. A
packet that arrives from your home network through WireGuard isn't from an Azure host, so the
lab puts a forwarder (dnsmasq) on the VM, which does ask from inside Azure.

</details>

<details markdown="1">
<summary>What would a VPN Gateway save you, and what wouldn't it?</summary>

It saves you patching and running a VM: Azure runs the gateway, with SLAs and zone redundancy. It
doesn't solve DNS. The DGX would still need a resolver inside the VNet, which means a DNS Private
Resolver ($180 a month) or a forwarder VM anyway. For one machine that's about $157 plus DNS against
about $14.

</details>

<details markdown="1">
<summary>Why is the tunnel "split", and what would change with AllowedIPs = 0.0.0.0/0?</summary>

With `AllowedIPs = 10.200.0.1/32, 10.60.0.0/16`, only VNet traffic goes through Azure. Everything
else (model downloads, apt, GitHub) uses your home connection at full speed. With `0.0.0.0/0`,
everything would go through a 1-vCPU VM and leave Azure as billable egress, and you'd need extra
rules to keep the tunnel's own UDP packets off the tunnel.

</details>
