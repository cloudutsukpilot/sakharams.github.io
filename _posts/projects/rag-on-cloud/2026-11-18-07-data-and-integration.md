A RAG system is only as good as the chunks it retrieves, and here every chunk comes from a Markdown file in Git.
That makes the data side unusually simple to own and unusually easy to get subtly wrong: Liquid tags, includes
and front matter all look like content to an indexer that doesn't know better.

## Data ownership and classification
{: #data-ownership-and-classification }

| Data | Owner | Classification | Source of truth |
|---|---|---|---|
| Posts (corpus) | Me | Public | The blog's Git repo |
| Chunks and vectors | Derived | Public | Rebuilt from the corpus |
| Golden question set | Me | Public (it's about public posts) | Lab repo |
| Eval results | Me | Public | Lab repo `results/` |
| Questions and traces | Me | Internal: whatever was typed | Log Analytics |

Only the last row needs care, covered in
[Security and Privacy](/posts/projects/rag-on-cloud/06-security-and-privacy/#privacy-and-data-protection-requirements).

## Data retention and deletion
{: #data-retention-and-deletion }

- A post deleted from the blog is deleted from the corpus container by the next sync, and the indexer's deletion
  detection removes its chunks (soft-delete metadata on the blob, so the indexer sees it go).
- The index itself disappears every time Search is removed between sessions; that's by design.
- Results files are kept indefinitely in Git: they're the lab's memory.
- Traces follow Log Analytics retention (an open question in Security and Privacy).

## Database schema and migrations
{: #database-schema-and-migrations }

There's no database; the "schema" is the search index, defined as JSON in the lab repo and applied by
`make index`:

| Field | Type | Searchable | Filterable | Notes |
|---|---|---|---|---|
| `chunk_id` | String (key) | | | Generated by the index projection |
| `parent_url` | String | | Yes | The post's public URL, used for citations |
| `title` | String | Yes | | The post title, also in the semantic configuration |
| `chunk` | String | Yes | | Chunk text, English analyzer |
| `chunk_vector` | Collection(Single) | Yes (vector) | | Dimensions of the embedding model |
| `published` | DateTimeOffset | | Yes | For "newest first" questions |
| `tags`, `categories` | Collection(String) | Yes | Yes | Agent tools can filter on them |

"Migrations" are new index versions: a breaking change (a new vector size, a different analyzer) creates
`blog-chunks-v2`, the indexer fills it, the API switches by config, and the old index is deleted. With a corpus
this small a full rebuild is cheaper than anything clever.

## Data validation and quality
{: #data-validation-and-quality }

What the sync checks before uploading a post:

- Front matter has a title and a date, and the post isn't `published: false`.
- Liquid tags and `{% raw %}{% include %}{% endraw %}` lines are removed; code blocks are kept (questions often
  ask about commands).
- The public URL is computed from the categories the same way Jekyll does, and checked against the built site.

After indexing: zero failed documents, every chunk has a vector, and the chunk count per post is within a sane
range (a post that becomes one giant chunk, or hundreds of tiny ones, is a parsing bug).

## Import and export requirements
{: #import-and-export-requirements }

Import is the corpus sync. Export is the golden set and the results, both plain files (JSONL for questions,
CSV/Markdown for results) so the homelab harness reads the same files. Nothing else crosses the boundary.

## External systems and third-party integrations
{: #external-systems-and-third-party-integrations }

| System | Direction | How |
|---|---|---|
| GitHub (blog repo) | In | Workflow on push to `main`, OIDC to Azure |
| Microsoft Foundry models | Out | Embedding skill and vectorizer from Search; chat from the API |
| Foundry Agent Service | Out | From the API in `foundry-agent` mode |
| Homelab `rag-api` | Out (eval only) | HTTPS through the homelab's private network, from the eval harness |

The homelab integration depends on the homelab's own RAG being built; until then Phase 4 stays blocked.

## Event and messaging contracts
{: #event-and-messaging-contracts }

There's no message bus. The only "event" is a push to the blog, which starts the sync workflow; the indexer then
runs on a schedule (or on demand from `make index`) and picks up changed blobs by their last-modified time. A
queue would only matter if ingestion had to react within seconds, and nobody needs a new post searchable that
fast.

## Backup and restore strategy
{: #backup-and-restore-strategy }

Nothing in Azure is backed up, on purpose. Every piece of state is either in Git (posts, index definitions,
golden set, results) or derived from it (blobs, chunks, vectors). "Restore" is the rebuild in
[Product Planning](/posts/projects/rag-on-cloud/03-product-planning/#phase-0-steps), step 4, and its time is a
measured metric.

## Data migration and reconciliation
{: #data-migration-and-reconciliation }

Reconciliation runs after every sync and every index rebuild:

```text
posts published on the site  ==  blobs in corpus/        (sync is complete)
blobs in corpus/             ==  distinct parent_url in index   (indexing is complete)
```

A mismatch fails the workflow. The only "migration" is moving between index versions, described in
[Database schema and migrations](#database-schema-and-migrations).

## Checklist
{: #checklist }

- [ ] Sync strips Liquid and skips unpublished posts
- [ ] Public URL computed like Jekyll and checked against the site
- [ ] Deletion detection removes chunks of deleted posts
- [ ] Index JSON versioned, with a v2 path for breaking changes
- [ ] Chunk size and overlap chosen and recorded
- [ ] Reconciliation counts checked after every run
- [x] Golden set stored as JSONL readable by both harnesses
